# Background work on demand

The default `BACKGROUND_WORK_MODE=demand` stops optional analytics, engagement ingestion, repost analysis, automatic tuning and provisional snapshots when the related authenticated feature is not being used. Successful authenticated analytics/metrics/stats requests request an immediate refresh and renew a two-minute activity window. Repeated requests coalesce coordinator writes to at most one per category per minute. Anonymous traffic, refused requests, health checks, connection status, credits, notifications and recovery polling do not renew demand. Explicit `continuous` mode is an operator override; it is not the default.

A small server-owned `system_runtime/background_activity` document shares activity between the API and standalone worker. Its timestamps expire in memory without writes or deletions. It contains no user identifiers, tokens or media. Client permissions remain governed by the existing admin-only catch-all rules.

Requested publishing/upload/media-transform work and engagement campaigns use bounded native Firestore listeners as eligibility hints. Idle timer ticks inspect the current snapshot in memory; future timestamps and retry cooldowns are evaluated against the clock. Actual processors continue to fetch and validate authoritative records before acting. Paused schedules stay paused. Already requested schedules, recovery and pending financial work continue without an open browser. API and standalone worker share the existing queue/metrics leases, and the standalone worker uses the canonical promotion scheduler.

Latency persistence requires new request samples and active authenticated use. Its pruning counts via the index and fetches only bounded expired document identities, rather than downloading every stored statistics record every minute. Empty successful worker status updates are not persisted. Expired lock cleanup transfers only expiry fields. Necessary lease coordination, retention cleanup and daily reporting remain bounded background activity; this change does not promise zero Firestore usage or eliminate retained-image storage charges.

YouTube refreshes preserve the service receiver, derive the owning account for trusted background work, refuse another owner's content during a manual owner refresh, recognize recent ISO timestamps and fetch only the YouTube/account fields. Existing manual routes remain fresh reads. No provider or publishing operation is started by the verification tests.

Local validation includes fake-clock idle/due/retry tests, actual publishing entry-point guards, ownership and callback tests, and native Firestore emulator listeners across two clients. The emulator test refuses any non-loopback host and uses an isolated demo project. See `reports/demand-driven-background-20261117/README.md`. Production savings must be measured after deployment; historical billing and the prior audit are not post-change proof.
