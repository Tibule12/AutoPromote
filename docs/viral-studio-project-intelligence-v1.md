# Studio Project Intelligence V1

This branch adds a bounded, CPU compatible representation of what source files may contain and how they may relate. It records human declarations and already stored source shot artifacts. It does not create an edit, select a take, render media, or infer scene facts automatically.

## Three separate kinds of state

1. **Immutable source evidence.** `studioSourceShotArtifactService` already stores a user scoped, content addressed source shot projection. The new evidence references identify an authorized source binding by source byte SHA-256 and, where applicable, an existing artifact SHA-256, engine and dependency SHA-256. A raw human transcription is recorded as `human_transcription` evidence with a source content hash and is explicitly a user declaration, not a model output or verified acoustic truth. New analyses must create new artifacts; they cannot replace an existing evidence record in an intelligence revision.
2. **Project Intelligence interpretation.** A `ProjectIntelligenceRevision` contains sparse assets, capture groups, typed assertions, clock mappings, dialogue units, supplied beats, candidate source ranges and continuity observations. Its `revisionId` is a SHA-256 of deterministic JSON. The server stores an immutable record and current head under the authenticated user. Each revision retains every record from its base verbatim. A correction appends a new record with `supersedes`; a rejected or verified state requires a reviewer matching the authenticated owner. Superseded claims remain in stored history. Unknown, proposed, verified and rejected are explicit states, without invented probabilities.
3. **Canonical edit state.** V1 is a whole-project intelligence snapshot. The Studio project document therefore holds zero or one `{revisionId, manifestHash, dependencyDigest}` reference in the existing `projectIntelligenceRefs` array. Registration checks that the reference resolves to an immutable, matching record in the same user and project scope. It carries no dialogue arrays, masks, embeddings, waveforms, dense tracks or per frame observations. The existing 512 KiB bound remains. Existing documents without this optional field still validate. History restore carries forward the current authoritative reference. Multiple concurrent V1 revision references are invalid, even if their hashes differ.

The contract is in `src/services/studioProjectIntelligenceContract.js`. `studioProjectIntelligenceService.js` owns registration and reads. `studioProjectIntelligenceRoutes.js` exposes authenticated registration, current summary, and exact revision retrieval at `/api/studio/director/projects/intelligence`. The registration body is limited to 270 KiB and the validated revision to 256 KiB. The service requires an existing registered canonical project head, verifies each asset against the existing user/project/source byte hash binding, and checks each source shot artifact against its immutable stored record. The user scope is taken from Firebase authentication. Client supplied model or heuristic origin labels are rejected by this route; model produced intelligence needs a later server controlled artifact writer. A filename, storage path, signed URL, or type declaration is not identity.

The existing project head is itself a canonical snapshot registered by an authenticated client, and the source binding proves that this account supplied the media bytes under the claimed project and asset IDs. These checks do not independently prove that a browser declared project name reflects a separate server created project, or that a human assertion is factually correct. They preserve that distinction in provenance and review state.

## Capture, sync and conflicts

Each asset names its owner/project, stable ID, source binding, content hash, duration, media type, stream identities, timebase, frame or sample rate, technical metadata and declaration provenance. A capture group is a versioned belief about one recording event; ungrouped assets remain valid. Typed relations include same capture, alternate take, external audio, simultaneous recording, scene/take membership, camera role, reaction, insert, cutaway, shot role and camera motion. Shot roles and camera motion use bounded enums, including `unknown`. Assertions carry evidence IDs, method, author, state, uncertainty and optional supersession. The summary returns these fields so a consumer can distinguish a verified claim from a proposed or unknown one.

Clock mappings use 90 kHz source ticks and exact integer rational arithmetic:

`referenceTick = offsetTicks + sourceTick × rateNumerator / rateDenominator`

The contract stores coverage interval, fit residual, method, evidence, uncertainty and review state. `mapCaptureClockTick` returns exact numerator/denominator plus floor and remainder, so fractional drift is not silently rounded away. A mapping is optional. The mini film fixture maps external audio with 9,000 ticks offset and a `1,000,100/1,000,000` rate: source tick 900,000 maps to 909,090, whereas an offset only mapping would give 909,000. Its 90 tick residual remains explicit. No sync is asserted for the other source relationships.

The validation findings surface conflicting verified single value scene/take/camera claims and a verified `same_capture` component that also contains an `alternate_take` claim. A conflict sets `planningBlocked`; the data remains readable for human correction. No assertion is silently selected as truth. Missing beat coverage and verified continuity mismatches also appear as findings. These are sparse declared comparisons, not automated detection or universal quality scores.

### Supersession identity and state

A successor is a new immutable record in a later revision; it never edits the prior record. Its `supersedes` target must be present in the preceding revision. The target must also be the same logical claim:

| Record                 | Required stable identity across supersession                                                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture group          | `captureEventId` and `anchorAssetId`; the anchor remains a member. Other membership may be corrected.                                                                             |
| Relationship assertion | Relation, `from` endpoint, `to` endpoint kind and source range. A scene, take, camera, shot role or camera motion _value_ may change; asset or beat relationship targets may not. |
| Clock mapping          | Source stream and reference stream IDs. Fit, offset, rate and covered interval may be corrected.                                                                                  |
| Dialogue unit          | Stable `dialogueKey`, origin and screenplay unit ID. Reviewed wording and candidate takes may change.                                                                             |
| Beat coverage          | Beat, asset and exact source range. A different beat or range is a separate candidate; reject the old candidate and add the new one if replacing it.                              |
| Continuity observation | Beat, subject, continuity key, observation type, asset and source range. The observed value may change.                                                                           |

The allowed state transitions are: `unknown → proposed | human_verified | rejected`; `proposed → proposed | human_verified | rejected`; `human_verified → human_verified | rejected`; `rejected → human_verified`. `unknown` can never supersede another record. A verified or rejected successor requires an owner human review. A proposed successor cannot deactivate a verified or rejected decision. Reopening a rejection requires another explicit human verification. The active view applies these rules as well as validation, so an invalid lower-trust successor cannot hide a human decision.

## Dialogue, coverage and controlled examples

A dialogue unit has one base shape for `scripted` and `unscripted` content. A scripted unit may name a screenplay unit; an unscripted one leaves that ID null. Reviewed wording is separate from candidate utterance evidence. Each candidate names its asset, exact half open source range, evidence ID and optional take assertion. Changing wording requires a new intelligence revision and does not rewrite the raw declaration or a future transcription artifact.

The **mini film** fixture has two takes with Camera A, Camera B and external audio, plus a reaction, insert and room tone. Take 1's capture group is human verified; Take 2's is proposed. Scene, take and camera assertions are explicit. The reaction relation is `unknown`. The `leaving` beat has wide, close and reaction candidates with exact source ranges and evidence IDs; the close candidate warns that camera audio is bad and external audio is only proposed. The `exit` beat has no candidate and is reported missing. Two verified prop observations disagree on the cup color; another deliberately conflicting pair asserts that Take 1 cameras are both same capture and alternate takes. The fixture therefore blocks dependent planning while retaining all claims and evidence.

The **build in public promo** fixture has talking head, screen recording, failure, fix, result, product UI and CTA sources. Supplied `result_tease`, `process`, `problem`, `fix`, `proof`, `payoff` and `cta` beats map to source ranges and user declaration evidence. The mapping is a candidate inventory, not an edit or ranked recommendation.

`summarizeProjectIntelligence` answers asset/stream inventory, active captures and assertions with their states/evidence, clock mapping, dialogue alternatives, candidate coverage, explicit missing beats and findings. A consumer must show unknown values as unknown. The exact stored revision remains available for audit, including superseded claims.

## Capability boundary and future work

The capability registry now has a separate `directorPermission` object with `directorCommandSupported`, `serverValidated`, `rendererVerified` and `releaseEnabled`. `isStudioCapabilityDirectorAllowed` requires every flag and current executability. Only the existing, bounded, human reviewed split and edge trim proposal path is enabled; proposal preparation and AI actor command validation use this gate. The per-proposal authenticated review and server replay remain separate requirements before application. Other Director capability flags remain disabled. Manual capability behavior is unchanged. Intelligence registration cannot call the command kernel or mutate a timeline.

The first server-owned CPU analysis artifact bridge is documented in [Studio analysis artifacts V1](viral-studio-analysis-artifacts-v1.md). The opt-in source-shot job queue, owned-source path, resume and cleanup are documented in [Studio source-shot analysis jobs V1](viral-studio-analysis-orchestration-v1.md); they have not been deployed to a cloud worker. Broader Phase 3 orchestration, new model inference, UI editing of intelligence, automatic story or continuity detection, creative planning, AI editing and GPU jobs remain unimplemented. A future GPU worker would use the same artifact boundary. Neither path should write a trusted intelligence claim through the browser declaration route. Cam Combiner is unchanged.

The original `source_shot_artifact` adapter still bridges its stored `artifact.engine` to the V1 evidence field named `modelRevision`; its `configHash` is null because the older artifact has no separate configuration digest. New `analysis_artifact` references resolve to the server-owned record with those fields separated. Only the existing CPU source-shot worker writes this V1 artifact type; there is no general producer API or model job.
