# Viral Clip Studio capability and composition boundary

Registry version: **1**. This records the Viral Clip Studio execution paths and known gaps for the AI Director foundation. The machine-readable source is `frontend/src/components/studioCapabilities.js`; 3D field details are in `frontend/src/components/threeD/studio3DParity.js`. A validated input field or a visible control does not establish render support.

## How to use the registry

`getStudioCapability(id)` returns a versioned entry or `null`. Every entry declares a parameter schema, project operation type, required evidence, read and write sets, preview engine and fidelity, final engine, cost and resource classes, fallback, release state, limits, compatibility, conflicts, renderer or template version, and evidence suite. `executable` means a product execution path exists. `limits.commandKernelMigrated` identifies the smaller set that the new headless command executor accepts. Unknown capabilities and unsupported entries fail closed in the command executor.

`exact` describes a decision or state contract whose meaning is shared across the paths named in the entry. It does **not** promise pixel-identical preview and export. `approximate` means the operation runs, with known preview/export or parameter differences. `unsupported` means there is no usable final path for the claimed effect. `foundation` is the migrated command family; `legacy` uses an existing UI/render path; `unverified` means the available repository evidence does not establish that its external renderer can currently run.

## 3D field parity, version 1

The field matrix classifies **every normalized 3D scene field**. The paired browser/Blender numeric pose fixture tests timeline, keyframe interpolation and preset pose; it does not test image pixels, materials or final alpha. There is no Blender binary in this checkout's test environment, so the visual defects below remain classified rather than claimed fixed.

These unsupported controls still exist in legacy 3D project state and UI. The Advanced inspector now states the export limitations at the point of editing. They must not be selected by a Director command until a renderer implementation and paired preview/export proof exist. The registry exposes `unsupportedSceneFields` and `unsupportedSceneModes` for that future validation gate. The current validated JSON plus owned-artifact boundary remains intact; arbitrary Blender Python is not an input.

## Current composition order

The final worker builds one video chain in this order:

1. Base edited video and reframe/speed processing.
2. Regular video, image and text overlays. Their saved order is reconnected after media-specific filter creation; this is the only cross-media order implemented for regular overlays.
3. One generated 2D motion graphics alpha layer.
4. Validated, signed 3D alpha clips sorted by their own `layerOrder`.

Source: `python_media_worker/main_media_server.py` near `overlay_order`, `motionGraphics` and `threeDGraphics`; the browser payload forwards these as separate `overlays`, `motionGraphics` and `threeDGraphics` fields. `src/services/studio3DService.js` resolves and sorts owned 3D jobs. The current canonical document adapter preserves these categories as typed layer references and records `compositionStage` values `worker_overlay`, `worker_motion` and `final_alpha`. That stage field describes legacy behavior; it is not a new universal compositor.

The future document can represent video, graphic, subject matte, foreground subject and 3D/motion layers with explicit programme ranges, layer IDs, asset references, mask references and ordering constraints. A compiler should reject cross-stage reordering until the final worker has one defined composition graph and a preview/export conformance test. Existing `layerOrder` cannot safely be reinterpreted as global z order.
