The shared worker now reuses exact owned source/preparation work and renders independent layers with bounded parallelism. The same 45-second native request completed locally in **7m21s**, compared with **12m38s** before the change: **41.76% less elapsed time**. Both finished MP4s are byte-identical (`ce7bdfe0dbc1055213df5cc46ee8cb1bab23eacadc29758fe8f8fe21171926df`). Complete decoded RGBA and PCM hashes also match. Resolution, picture clocks, masks, graph order, sound and final encoding settings are preserved.

This is one local A/B pair using the actual production request, exact retained uploaded artwork/score and verified original video bytes. Source adapters use loopback instead of cloud downloads. The local GPU is a Quadro M1200; the production deployment specifies an RTX PRO 6000. Short regression/profile checks ran intermittently during both variants. These results do not establish production throughput, queue latency, cold-start behaviour, dollar savings or load capacity. Layer preparation dominated the original local export. Repeated camera normalization and exact trim/loop/hold/speed commands now share their result within the current export. This uses the actual owned input and complete commands; it does not trust a claimed content hash or share data across jobs. Still layers retain one immutable resized surface and one held-frame byte buffer. Moving video and multi-sample shutters retain their individual frames. Independent video/image preparations run through the existing renderer; the original ordered graph still applies every matte and composition step.

Parallelism respects container CPU quota and is capped at two preparations on CPU fallback and four on the configured GPU worker. The local comparison used two. A failed export cancels queued preparations and joins running encoders before cleanup. The final fail-fast/completion-order adjustment is separately exercised by the final scheduling/native-worker tests; the full-film A/B used ordered future waiting. Phase durations, reuse counts and throttled layer progress are recorded, replacing the long silent layer-preparation period after the colour step.

The actual **293,713,235-byte podcast** now produces its accurate original-clock paused PNG locally: **1.55s cold / 0.43s cached**, with about **30 MiB API RSS growth**. Sampled combined API/FFmpeg peak RSS was **154.4 MiB**, under a 96 MiB Node heap setting. This exercises the real source bytes and decoder with a local owned-storage adapter; live GCS authorization/transfer for this larger source still needs release verification. The service streams checksum-validated, generation-pinned bytes to private disk and checks their SHA-256. It retains per-owner/global admission, a 512 MiB source ceiling, 640 MiB total disk reservations, a 32 MiB legacy derivative allowance, a 64 MiB free-space floor, pending-download reservations, cancellation cleanup and a two-minute inactive TTL. RAM-backed temporary storage retains a smaller allowance. Existing local-only protocols/demuxers and picture sampling are unchanged.

Additional GPUs primarily provide capacity for simultaneous jobs in this architecture. Our measured bottleneck includes CPU-side layer work. NVIDIA documents the importance of accelerating the complete decode/process/encode pipeline and avoiding transfers; Adobe likewise describes sharing editing work between CPU and GPU. [NVIDIA pipeline guidance](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/ffmpeg-with-nvidia-gpu/index.html), [Adobe GPU processing](https://helpx.adobe.com/premiere/desktop/get-started/download-and-install/mercury-playback-engine-gpu-accelerated-in-premiere.html). [Cloud Run GPU billing](https://docs.cloud.google.com/run/docs/configuring/services/gpu). No new hardware allocation or spending recommendation is justified by this local test alone.
