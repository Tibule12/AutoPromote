## Owner retry and provider verification repair

The owner retried the deployed diagnostic release `cfba8537` and received **`webhook_contract`**. This establishes that state validation and the token exchange passed, and that the returned webhook failed a local contract check. The particular field was not captured; it is not evidence of an expired link or bad client secret.

The original check incorrectly required non-null `webhook.application_id`, although [Discord's webhook structure](https://docs.discord.com/developers/resources/webhook#webhook-object) documents it as nullable. The repair verifies the actual bearer grant through **GET `/api/v10/oauth2/@me`**: matching application, both `identify` and `webhook.incoming`, future expiry, and a valid human identity from that same grant. It then performs a **GET** of the canonical webhook endpoint and matches webhook ID, channel, guild, incoming type, and any non-null application ID. It does not execute the webhook or trust a browser-supplied capability/URL. The scope echo in the exchange response is not used in place of authenticated grant information. [Current authorisation information](https://docs.discord.com/developers/topics/oauth2#get-current-authorization-information).

Only after those checks does the server persist an encrypted webhook and explicit version-two OAuth application binding. Dispatch rechecks that private binding and the live webhook's ID/channel/guild/type; any conflicting non-null application remains rejected. Historical destinations without the new verified binding retain their strict application-ID requirement. No legacy destination, balance, billing record, subscription or Rules document is migrated or rewritten by this repair. Failures now identify the specific verification step using closed support categories.

**42 Firestore-emulator integration tests pass**, including nullable application IDs with no scope echo, wrong application, missing permissions, expired/invalid grants, missing identity, changed live webhook metadata, dispatch binding and legacy rejection. ## Passthrough-scope correction

The next live retry on `4d617fd7` passed webhook shape and OAuth application validation, then returned `grant_scopes`. The repair had incorrectly required `webhook.incoming` in the bearer's persistent scope list. [Discord identifies it as a passthrough scope](https://docs.discord.com/developers/topics/oauth2#authorization-code-grant): the specialised code exchange issues the publishing webhook capability. Identity verification now requires `identify`; publishing still requires the webhook from that same server-bound exchange and its independently checked live ID/channel/guild/type/application. No browser claim, arbitrary webhook, missing webhook, invalid token or mismatched application is accepted.

The emulator and actual App fixtures now use a bearer with only `identify` alongside the nullable-ID webhook. Malformed scopes, missing identity permission and all webhook/application mismatches remain rejected. Earlier statements requiring both scopes in the grant describe the superseded implementation. Live connection success still requires the owner's next retry; the original response's precise failing field was not captured.
