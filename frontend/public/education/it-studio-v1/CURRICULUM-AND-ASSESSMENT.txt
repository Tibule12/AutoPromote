ASSESSMENT: CONCEPT FIRST, EDIT SECOND
Suggested supplementary rubric (teacher may adapt, not an official CAPS rubric):
40% technical correctness: valid representation, state, control flow, array bounds, stable identities, correct query result.
30% explanation and transfer: justify a step, predict the next state, solve an unseen input and diagnose a deliberate defect.
20% editable construction: named native layers, exact timings/keys, reproducible controls and complete export.
10% accessibility and responsible use: readable text, understandable audio/transcript, permitted assets, fictional data, disclosed assistance.
Do not award algorithm marks simply because an imported composition plays. Require a trace and a short independent explanation.
Teacher review: watch each entire native result and its corresponding actual Studio walkthrough; check keys at transitions, labels, sequencing and misconceptions.

6. Animate a loop and its changing variables
Initialise i = 0 and sum = 0. While i is less than 3, add values[i] to sum, then increment i. The visits are indices 0, 1 and 2. Final state: i = 3, sum = 12. Reading an element does not remove or change it. The condition prevents an out-of-bounds access.
Exercise: Change the original example to [3, 5, 7]. Submit a trace table before adjusting text states and token timing. Show final i = 3 and sum = 15. Explain why a fourth read would be incorrect.
Q1 (2 points): Predict the final sum if it starts at 10.
Reasoning guide: 22, because 2 + 4 + 6 is added to the initial 10.
Q2 (3 points): Why does i = 3 stop the loop?
Reasoning guide: There are three elements at indices 0–2. The condition i < 3 is false at 3; values[3] must not be read.
Q3 (2 points): How many reads and additions occur?
Reasoning guide: Three of each. The source array remains [2, 4, 6].
Teacher review: Pause before each update and ask learners to predict i and sum. Assess the trace before the animation. Copying an imported recipe without predicting states does not demonstrate loop understanding.

7. Make a validation bug visible
The Byte Lab accepts one to three decimal digits after trimming and then requires a numeric value from 0 through 255. The input 256 passes the format check but fails the range check. An incorrect maximum of 256 accepts a nine-bit number, not an eight-bit unsigned byte. Fix the maximum, rerun the failing case and test valid boundaries. The illustrative broken path is labelled BUG; it is not the behaviour of the supplied working app.
Exercise: Create a test table including blank input, 0, 255, 256, -1, 18.5 and 18. Animate two contrasting decisions, label the deliberately broken rule and show the retest after correction.
Q1 (2 points): Which check rejects 256 in the supplied app?
Reasoning guide: The range check; 256 has an accepted digits-only format but is greater than 255.
Q2 (4 points): Give expected results for 0, 255, -1 and 18.5.
Reasoning guide: 0 and 255 are valid and produce 00000000 and 11111111. -1 and 18.5 are rejected by the digits-only format guard.
Q3 (2 points): Why is silently dropping the ninth bit not a valid fix?
Reasoning guide: It changes the value and hides invalid input. Reject it or define a different numeric representation explicitly.
Teacher review: The film contrasts a deliberately broken rule with the working Byte Lab guard. Ask the learner to name the defect, input, expected result, observed result and correction. Do not confuse format validation with proof that user data is true.

8. Animate bubble sort, comparison by comparison
This ascending, zero-based example swaps only when the left value is greater than the right. After pass 1, [1, 4, 2, 5] has the largest value fixed on the right. Pass 2 produces [1, 2, 4, 5]. Pass 3 performs one comparison without a swap and stops. There are six comparisons and four swaps. The strict greater-than rule preserves the order of equal keys; this four-distinct-value film alone does not prove stability.
Exercise: Trace [3, 2A, 2B, 1] on paper, then rebuild the Studio animation. Keep equal values in their initial order, count comparisons and swaps, label each pass and explain the rule without relying on colour.
Q1 (3 points): Write the array after pass 1 and explain why its last value is settled.
Reasoning guide: [1, 4, 2, 5]. Each comparison passes the larger value rightward, so the largest ends in the final slot.
Q2 (2 points): Count comparisons and swaps separately.
Reasoning guide: 6 comparisons and 4 swaps. Pass comparison counts are 3, 2 and 1; swap counts are 3, 1 and 0.
Q3 (3 points): Why should equal values not swap in a stable ascending version?
Reasoning guide: Strict > avoids exchanging equal keys, preserving their original relative order. Demonstrate with labelled duplicates, not just two indistinguishable 2s.
Q4 (2 points): What prevents j + 1 going out of bounds?
Reasoning guide: Use j < end with end initially n - 1, then reduce end after each pass. The largest accessed index is end.
Teacher review: Reject an attractive animation if it swaps non-neighbours, loses a value, changes a fixed index or labels a comparison as a completed swap too early. Ask for a prediction on a new input. The zero-based pseudocode is an original teaching reference; adapt implementation to the class language.

9. Show how a database relationship makes a result
Teams.id and Entries.id are primary keys in different tables. Entries.teamId references Teams.id. Joining matching IDs adds the team name to each entry. Filtering score >= 70 keeps entries 102 and 103; ordering score descending returns Prism 80 then Orbit 75. The storyboard presents the query conceptually; it is not a claim about the database engine’s physical execution order. Studio animates the explanation and does not execute SQL.
Exercise: Add an entry for team 20 with score 72 in the SQL file. Predict the result, run it in an approved classroom DBMS and update the editable explanation. Discuss ties and add a secondary ORDER BY key if you need a deterministic tied order.
Q1 (3 points): Why can Entries.teamId contain 10 more than once?
Reasoning guide: Different entries may belong to the same team. A foreign key may repeat; each primary key identifies one row in its own table.
Q2 (3 points): What does the query return and why is Prism first?
Reasoning guide: Prism 80 then Orbit 75. Both scores meet >= 70, and descending order places 80 before 75.
Q3 (2 points): Would an unmatched entry appear in this INNER JOIN?
Reasoning guide: No. INNER JOIN requires a matching Teams.id. A properly enforced foreign-key constraint prevents such an orphan from being inserted.
Q4 (2 points): Does moving a highlight in Studio run the SQL?
Reasoning guide: No. SQL is independently executed in the supplied example; Studio supplies the visual explanation.
